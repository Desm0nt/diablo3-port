# Diablo III: Eternal Collection (Switch) → нативный Android: состояние и журнал

Подход тот же, что у DOOM 2016 / DOOM Eternal / Xenoblade 2 (журнал DOOM Mobile — `docs/doom/PORT_JOURNAL.md` в репозитории github.com/Desm0nt/doom-port,
журналы портов DOOM Eternal и Xenoblade 2 не опубликованы): ARM64-код игры исполняется напрямую, NSO патчится
офлайн (x18/TLS/SVC/cntpct), `nn::` — HLE, NVN → Vulkan, шейдеры офлайн. Хост — клон дерева XC2 (`dm/`, ветка `d3`, от
`6202ff6`), сборка `DM_GAME=d3` = «тонкое» ядро DOOM (`DM_GAME_DOOM`) + `DM_GAME_D3`. Главный референс по SDK 8.2 —
nxnative (seedds, MIT), профиль Link's Awakening `work/reference/nxnative/dm/games/01006BB00C6F0000` (**тот же билд sdk
`3ae34e68…`**).

## Разведка (02.11.2026)
- SDK **8.2.0** (NVN 8.2, API 53 — раскладки объектов как у DOOM 2016 / D2R, не NVN 55 Eternal), libcurl, libz.
- Модули только `main` + `sdk` (без subsdk → GLSLC и nn::movie нет). build-id main `2607a74f…`, sdk `3ae34e68…`.
- main: text 0xc72b90, ro @0xc73000 (0x4249c4), data @0x1098000 (0xc4a14); 550 импортов: HLE по имени 297, экспорт sdk 249,
  остальные — `__rel_*` (закрывает загрузчик). Новое по сравнению с прошлыми портами: `nn::nfp` (amiibo), `nn::ldn`,
  `nn::friends`, `nn::swkbd`, `nn::socket`/`nifm`/`ssl`/`nsd` (Battle.net через libcurl).
- npdm: prio 44, core 0, **SystemResourceSize 0x1000000** → VAMM включён (как у Eternal), стек 1 МиБ.
- RomFS (база + BKTR апдейта, IVFC ок): 37 файлов, 16.0 ГиБ — архивы Blizzard `CPKs/*.cpk` (Act1..5, Common, ClientCommon,
  CoreCommon, ServerCommon, `enUS_*`) и `Update/CPKs/Patch2_6_5..2_7_7.cpk`. Магия `0xA1B2C3D4`, версия 7, сектор 0x4000.
  В main пути `%s\CPKs\%s.cpk`, `%s\Locale.cpk`, `%s\Update.cpk`, `%s\CPKs\PVPCommon.cpk` (обратные слэши).
- Консольная сборка: онлайн опционален (`PS3OfflineMessage`, `OfflineIcon`, `ConsoleBattlenetAccountLinkScreen`).
- Патч NSO: main 4 420 сайтов, sdk 11 277 (93 гейта); `equiv.py` — **0 расхождений**, мутаций поймано 300/300 на обоих.

## Как собрать и запустить
Всё это делает `setup.bat` / `setup.sh` (`tools/setup_d3.py`, см. `docs/INSTALL.ru.md`); по шагам вручную (ключи: `NX_PROD_KEYS=<prod.keys>`):
```
python tools/exefs_nsp.py "<update nsp>" work/exefs-update        # main, sdk, main.npdm
python tools/nso_symbols.py work/exefs-update main sdk              # *.raw, *.symbols.json
python tools/romfs_d3.py list|extract "<base nsp>" "<update nsp>" work/romfs   # база + BKTR, IVFC
DM_TARGET=android PYTHONUTF8=1 python dm/tools/patch_nso.py work/exefs-update/<mod> work/patched <mod>   # main sdk
PYTHONUTF8=1 python dm/verify/equiv.py work/patched <mod> work/exefs-update/<mod> --jobs 12
```
Дальше (в работе): ридер CPK и шейдеры (`docs/d3/CPK.md`, `docs/d3/SHADERS.md`), сборка `DM_GAME=d3` (`docs/d3/D3_GATES.md`).

## Ночь 02.11.2026: телефон (Mi 14 Ultra, Turnip 27) — меню и геймплей
Данные: RomFS 16 ГиБ → `/sdcard/Download/Diablo3Mobile/romfs/{CPKs,Update/CPKs}` (adb push по USB рвался broken pipe —
дозаливка по файлам со сверкой размеров), `dm/out` = `work/patched`, `dm/shaders` = `work/shaders-vk` (1 323 `.xgs`).
`dm/env` — ФАЙЛ (KEY=VALUE), не каталог: по ошибке был создан каталогом, и никакие DM_* не доходили до игры.

| # | Симптом | Причина | Исправление |
|---|---|---|---|
| 1 | SIGSEGV null+0x1008 в потоке чтения (main 0x765d7c) / FORTIFY pread count<0 | игра запущена, пока CPK ещё доливались | долить данные; `DM_FS=1` теперь пишет и неудачные open/stat |
| 2 | **AUTOSAVE висит** (3 из 5 запусков; счётчик fps на экране застывает, кадры игры прекращаются через ~4 с) | поток логики крутит `nn::os::YieldThread`, пока NVN counter report кадра N−3 (main 0xe72b0) = 1, и NVN не вызывает; при `DM_GFX_DEFER_EVENTS=2` отчёты/события публикуются только при ретайре слота, который запускает следующий NVN-вызов → взаимная блокировка. На Switch GPU пишет отчёт сам | для D3 `DM_GFX_DEFER_EVENTS=0` по умолчанию (`jni_android.c`): 0 зависаний из 6+, fps тот же. Правильный фикс (ретайр слотов по таймеру в потоке трансляции, чтобы вернуть перекрытие) — в работе |
| 3 | геймплей 34 fps | 12.5 МБ снапшотов буферов на кадр | zero-copy для D3 по умолчанию: **45 fps** (снапшоты 2.4 МБ/кадр), UBO по-прежнему снапшотятся |

Итог ночи: AUTOSAVE → «PRESS ANY BUTTON» → главное меню (**60 fps**, GPU ~5–8 мс) → сложность → загрузка → ACT I →
геймплей на дороге к Новому Тристраму (**~45 fps**, GPU ~10 мс, CPU трансляции ~17 мс, одна синхронизация GPU на кадр `sync_q`),
персонаж ходит/бьёт, крэшей при входе на карту в 5 прогонах нет. Без `DM_GFX_DEFER_EVENTS=0` прогон, в котором автор видел
крэш при загрузке, не воспроизводился.

Инструменты: `tools/hangcheck.sh <имя> [сек] [ENV…]` (идут ли кадры до конца), `tools/gp_ab.sh <имя> [ENV…]` (скриптом в геймплей
Акта 1 существующим героем, медиана последних 15 PERF), `tools/shots.sh`. Маршрут клавишами: `DM_KEYS=A@18,A@26,A@34,A@42,A@50,A@58`
(+ `LSU@72+3` и т. п. — левый стик). A/B без эффекта в геймплее: `DM_NVN_SYNC_LAG=1`, `DM_GFX_SUBMIT_CHUNK_US=1000`.
Пад: раскладка Joy-Con для D3 (без FIRE/обзора DOOM). Тап по UI как в d2r-mobile невозможен напрямую: main D3 не импортирует
тач/мышь/клавиатуру (только npad) — нужен отдельный реверс фокуса UI.

### Под утро 02.11: 60 fps в геймплее, тестовый герой
| # | Симптом | Причина | Исправление |
|---|---|---|---|
| 4 | геймплей 45 fps, `sync_q` 60/с | единственный командный буфер кадра заканчивается `nvnCommandBufferSignalEvent`; при defer 0 он делает `complete_all` → GPU стартует только после трансляции всего кадра (кадр ≈ трансляция + GPU); при defer 2 синхронизацию делал `nvnEventGetValue` | `DM_GFX_IDLE_RETIRE` (субагент, a65c80d): поток nvn-translate по таймауту 1 мс ретайрит готовые слоты и пишет отчёты/события в память гостя сам (как GPU Switch), =2 — `nvnEventGetValue` не ждёт. D3 по умолчанию: `DEFER_EVENTS=2 IDLE_RETIRE=2 SUBMIT_CHUNK_US=0` (c3576b8): **60 fps**, CPU 17 → 5 мс, `sync_q` 0, AUTOSAVE 0 зависаний из 9 |
| 5 | через ~7 мин игры (present #26100) `FATAL SVC 0x2c mprotect …+0x20000 errno=12` (MapPhysicalMemory); перед этим `写保护缺页 54970 次` | исчерпан `vm.max_map_count` (65530 VMA). Трекер грязных страниц (`nvn_dirty.c`: текстуры `DM_GFX_TEX_DIRTY`, vcache) ставит пулы RO, а каждый write-fault снимал защиту с **одной страницы** посреди RO-участка → VMA режется на три (**+2 VMA на fault**); страницы текстур, которые больше не проверяются, остаются дырами навсегда. Ошибки `mprotect` трекер игнорировал (RO-страница с состоянием NONE → вечный цикл fault). Доп. источник: резерв гостевого AS без `MAP_NORESERVE` — RW-коммит ставит `VM_ACCOUNT`, обратный `PROT_NONE` его не снимает, и соседние `---` участки alias-региона (VAMM map/unmap) больше не сливаются. zero-copy ≤ 512 чанков (≤ ~1 тыс. VMA), wtrack ≤ 8 регионов — не причина | `nvn_dirty.c`: write-fault снимает защиту со всего выровненного блока (`DM_DIRTY_UNPROT_KB`, D3 = **64** КБ, 0 = страница) — потоковая запись = 1 fault на блок, дыры ≥ 64 КБ; `prep_write` — одним `mprotect` на участок; при ENOMEM fault/prep снимают защиту со всего RO-участка (без split), неудачный protect оставляет страницы RW и «всегда грязными» (`GEN_STICKY`); `nvn_dirty_relieve` — снять защиту со всех RO-участков (по `mprotect` на участок, VMA сливаются, страницы считаются записанными → текстуры перехешируются). Новый `hle_vma.c`: поток `dm-vma` раз в 5 с считает `/proc/self/maps`, строка `[vma] maps N / max …` раз в `DM_VMA_LOG` с (60; 0 — только события), при ≥ `DM_VMA_RELIEVE_PCT` % (75) — relief; `DM_VMA_WATCH=0` выключает поток. `hle_svc.c`: `MAP_NORESERVE` для резерва (`DM_AS_NORESERVE`, D3 = 1); Map/UnmapPhysicalMemory, MapMemory, SetHeapSize при ENOMEM → relief + повтор, затем `ResultOutOfMemory` 0xD001 вместо abort (Unmap — `MADV_DONTNEED`, страницы остаются доступными). Логика трекера проверена Linux-тестом (WSL): блок-дыры, fallback при ENOMEM, sticky, relief → 1 VMA. На телефоне не мерено |

Создание героя скриптом: титул A, главное меню X (Switch Hero), в выборе героя X (Create Hero, нужен второй X после анимации:
`DM_KEYS=A@18,X@38,X@55+0.3,X@64+0.3,A@74`), имя — диалог приложения «Hero Name» (swkbd → Android; игра сама предлагает имя),
на IME «DONE» (tap 2263,214), затем «OK» (tap 1883,723). Создана Danna (монах), вошла в Акт 1: 60 fps, GPU ~10–11 мс.
Внимание: не запускать новый `run.sh`, пока жив предыдущий фоновый — его таймер force-stop убивает следующий прогон.
Дальше: русский язык (AOC RU Language Pack 6 ГБ → монтирование AOC), A/B `DM_GFX_ZC_UBO_MIN=0`, порт DOOM-шных GPU-оптимизаций

## Меню ⚙ (настройки) для D3 — 02.11.2026
Перенесено из обновлённого меню DOOM 2016 (рабочее дерево DOOM Mobile на тот момент) то, что имеет смысл для D3. Отдельный диалог
`DmActivity.showD3Settings()` (у DOOM/Eternal/XC2 старый диалог не тронут); тексты — ресурсы `res/values/d3_settings.xml` (англ.)
и `res/values-ru/d3_settings.xml`. Настройки — `SharedPreferences "doom_graphics"` (графика/запуск) и `"doom_controls"` (пад);
«со следующего запуска» = переменные окружения до загрузки `libdm.so` (`applyDoomSettings`), `dm/env` по-прежнему главнее.

| Опция | Когда | Как доходит до игры |
|---|---|---|
| Язык этого меню (Как в системе / Русский / English) | сразу (диалог переоткрывается) | pref `ui_lang`, локализованный `Context` |
| Язык игры (система / ru / en-US / en-GB) | след. запуск | `DM_LANG` → `hle_oe.c GetDesiredLanguage`; язык ≠ en-US принимается, только если есть `<loc>_Common.cpk` в `romfs/CPKs` или в `aoc/<индекс>` (иначе en-US) |
| Разрешение игры = режим Switch: в доке 1600×900 / в руках 720p | след. запуск | `DM_OPMODE=1/0` → `GetOperationMode/GetPerformanceMode` (игра сама выбирает разрешение; в руках — ещё и handheld-стиль npad). **Режим «в руках» на телефоне ещё не проверялся** |
| Формат картинки: 16:9 с полосами (по умолчанию) / растянуть | сразу | размер `SurfaceView` (`applyAspectLayout`, как XC2); буфер 1600×900 масштабирует дисплейный контроллер (`gfx-present-native`) |
| Резкость FSR RCAS: выкл/слабая/средняя/сильная | след. запуск | `DM_GFX_SHARPEN` = 1.0 / 0.5 / 0.2 → `rcas.comp` в `vulkan_present.cpp` |
| Ограничение FPS: 30 / 60 (по умолч. 60) | след. запуск | `DM_PRESENT_MAX_HZ` → `hle_nvn.c present_cap_hz` + `nvn_pace_cap_hz` (наибольшая целая доля частоты экрана ≤ лимита; без переменной — старое правило «не ниже 60», другие игры не затронуты) |
| Драйвер Vulkan: системный / Turnip 27 (встроен) / пакеты из `Download/Diablo3Mobile/drivers/<имя>/` или `.zip` | след. запуск | `DM_VK_DRIVER` → `vk_driver.c`; строка «Сейчас используется» = `nativeDriverStatus` (`dm_vk_driver_status`); страховка от краша: `files/driver-trying`, после 2 запусков без первого кадра — системный драйвер + тост |
| Вибрация | след. запуск | `DM_RUMBLE` |
| Счётчик FPS, компенсация мёртвой зоны стиков | сразу | `doom_controls` `fps`, `move_dz` |
| Кнопка настроек: обычная / прозрачная + ползунок непрозрачности 1–100 % | сразу | `doom_controls` `gear_mode`, `gear_alpha` → `DoomPadView.drawBtn` (при нажатии — полная яркость) |

Чего нет и почему:
- **FPS > 60** — не предлагается: игра ставит present interval 1 при 60 Гц, логика интерфейса может считать кадры; без проверки
  на телефоне не включаем (вручную: `DM_PRESENT_MAX_HZ=120` в `dm/env`, плюс голос частоты в `vulkan_present.cpp` нужен свой).
  **30 fps не проверены на телефоне**: убедиться, что скорость игры нормальная (движок D3 считает время по часам, но не доказано).
- **Своё разрешение рендера / широкий формат** (как `DM_XC2_WIDE`) — нужен реверс создания render target'ов D3; не сделано.
- **3D-масштаб / DRS DOOM** (`DM_DOOM_RES`, `rs_*`) — это cvar'ы id Tech, к D3 не относятся.
- Отдельный выходной размер swapchain — бессмысленен: финальное масштабирование уже делает дисплейный контроллер (`gfx-present-native`;
  маркер `=0` вернёт GPU-blit nearest).

### Русский язык (AOC-пакет)
- Пакет RU `01001B300B9BF00A` = AOC-индекс **10**: 14 файлов в корне RomFS, 5.6 ГиБ — `ruRU_{Act1..5, Act1..5Cutscene, ClientCommon,

  main+0x738e0 ищет `data:/CPKs/<loc>_Common.cpk`, а при отсутствии — `aoc_<индекс>:/<loc>_Common.cpk`.

- Подготовка: `python tools/d3_dlc_romfs.py extract "<RU nsp>"` → `work/romfs-dlc/10/` (уже извлечено, 5.6 ГиБ, хэши ок); на телефон:
  `adb push work/romfs-dlc/10 /sdcard/Download/Diablo3Mobile/aoc/10`, затем в ⚙ «Язык игры: Русский» и перезапуск.
- Не проверено: монтируется ли AOC раньше первого чтения языка; язык, сохранённый в профиле (`SelectedTextLocale` /
  `TextLocaleOverride`), может перекрыть `GetDesiredLanguage` — тогда переключить в опциях игры.

## Самопроверка GPU-оптимизаций не на Adreno — 06.11.2026 (0.2.2-debug)

Пять точных оптимизаций D3 (`DM_GFX_REPORT_INPASS`, `DM_GFX_LAZY_CLEAR`, `DM_GFX_NAN_SAT`, `DM_GFX_LDC_CANON`,

живых HUD и звуке. Теперь `jni_android.c` ставит только `DM_GFX_D3PERF=1`, а решает движок (`xbg_game.cpp`
`d3perf_switches`):

* Adreno (vendor 0x5143) — все пять включены без проверки, как раньше (ноль затрат).
* Любой другой GPU — при инициализации движка, до первого кадра игры, `xbg_selftest.cpp` один раз гоняет на самом
  устройстве маленький тест (один командный буфер, одно ожидание с таймаутом 1 с; любая ошибка Vulkan или таймаут = FAIL)
  и выключает то, что не прошло:
  * `report_inpass` — проход 16×16: заслонка на левой половине, затем два occlusion-«бокса» без записи цвета/глубины;
    запрос закрыт и timestamp записан внутри прохода (как в пути in-pass) против старого пути (конец прохода). PASS:
    in-pass > 0 и совпадает с эталоном (с precise-запросами 128 и 256);
  * `lazy_clear` — двойник render pass с `loadOp`/`stencilLoadOp = CLEAR` поверх мусора (синий цвет, «непроходная»
    глубина, stencil 0x55), белый прямоугольник слева и зелёный сверху за ним (stencil EQUAL 0); два варианта: глубина 1.0 +
    LESS_OR_EQUAL на D24S8 и 0.0 + GREATER_OR_EQUAL (reverse Z) на D32. PASS: все пиксели как ожидалось;
  * `nan_sat`, `f2i_notrunc`, `ldc_canon` — compute-шейдер `xbg_selftest.comp` с точными шаблонами переводчика; варианты
    делают сами функции переписывания движка; PASS: те же биты, что у оригинала (NaN, ±inf, −0, 0.5, 2 … для клампа).
* `DM_GFX_SELFTEST=1` — тест и на Adreno (результат применяется), `=0` — без теста, тогда не на Adreno все пять выкл.
  `DM_GFX_SELFTEST_FORCE_FAIL=report_inpass,lazy_clear` (или `all`) — принудительный FAIL для проверки отката.
  Явный `DM_GFX_<имя>=0/1` в `dm/env` всегда главнее теста.
* Заодно не на Adreno копия результатов occlusion-запросов (`vkCmdCopyQueryPoolResults`) идёт с `WAIT_BIT`
  (`DM_GFX_QUERY_WAIT`, env главнее); тест пишет, отличалась бы копия без него.

В `boot.log` одна строка `[selftest] gpu "…" vendor … driver …: N ms: report_inpass PASS (in-pass 128/256, reference
128/256) | lazy_clear … | nan_sat … | ldc_canon … | f2i_notrunc … | query copy without WAIT … -> enabled: … disabled: …
(env wins: …) query copy WAIT=1`. На RTX 3090 (десктопный стенд с тем же кодом) всё PASS, 5–8 мс (первый холодный запуск
~250 мс из-за компиляции шейдеров). Шаблоны в шейдере проверяет `tests/selftest_patterns_test.cpp`.

### Значения проходов текстом: NVN GVAL (`DM_GFX_PASS_VALUES`)

Чтобы найти проход, после которого картинка на Mali-G57 становится чёрной, без скриншотов: на каждом кадре, который
снимает профайлер проходов (`DM_GFX_PASS_PROF`, не на Adreno его ставит `DmActivity`: `60 600 7200`), сразу после конца
каждого прохода compute-шейдер `xbg_pass_values.comp` читает сетку 32×18 текселей (576 точек, центры ячеек, ровно тот mip
и слой, куда рисовал проход) каждого color-вложения и depth и сводит их в числа. Только чтение: барьер до и после, без
смены layout и без лишних разрывов проходов; на непрофилируемых кадрах ничего. `DM_GFX_PASS_VALUES=0` — выкл., по
умолчанию (или `1`) включено, когда работает профайлер; на Adreno только если задан `DM_GFX_PASS_PROF`.

В `boot.log` после строк `NVN GPASS` того же сабмита (те же `frame= slot= i=`):

```
NVN GVAL frame=661 slot=3 i=7 att=0 kind=color fmt=97 1600x900 n=576 nan=0 inf=0 zero=12 neg=0 mean=0.21,0.18,0.15,1 max=3.2,2.9,2.4,1 serial=812 lvl=0 layer=0
NVN GVAL frame=661 slot=3 i=7 att=1 kind=depth fmt=129 1600x900 n=576 nan=0 inf=0 min=0.0123 max=1 mean=0.61 at0=0 at1=88 serial=813 lvl=0 layer=0
NVN GVAL frame=661 slot=3 i=8 att=0 kind=color fmt=95 800x450 skipped int fmt serial=820 lvl=0 layer=0
NVN GVAL frame=661 slot=3 i=9 kind=reads serials=812,813
NVN GVAL frame=661 kind=present serial=901 fmt=37 1600x900
```

`nan`/`inf` — тексели с NaN/±inf хоть в одном канале; `zero` — все хранимые каналы формата равны 0; `neg` — есть
отрицательный канал; `mean`/`max` — по конечным значениям (r,g,b,a); у depth `at0`/`at1` — ровно 0.0 / 1.0. `fmt` —
`VkFormat`, `serial` — серийник NVN-текстуры; `kind=reads` — какие уже нарисованные GPU текстуры читали draw/dispatch
прохода `i` (по возможности), `kind=present` — что показано на экран. Пропуски с причиной: целочисленные форматы,
MSAA, 3D, несемплируемые.

Как читать: идти по проходам кадра по порядку; виновник — первый проход, у которого на выходе `nan>0` (или всё в нули:
`zero=576`, `mean` ≈ 0), хотя строки GVAL тех serial, что он читает (`kind=reads`), были конечными и ненулевыми. Дальше
NaN/чернота только тянутся по цепочке. Если все GVAL нормальные, а экран чёрный — сравнить с `DM_GFX_PASS_VALUES=0`:
барьеры зондов сериализуют кадр и могут прятать гонку без барьера.

### 0.2.4: тип вершинного входа по формату атрибута (`DM_GFX_VTX_RETYPE`)

GVAL с Mali-G57 (0.2.3-debug, уровень снова чёрный под HUD): основной проход сцены нормальный (`mean` ~0.25, `max`
0.95), ломаются полноэкранные проходы в конце. Композит с bloom (`fs dc101f70`) выдаёт вместо сцены почти ровный цвет
тумана, копия `fs 22e0cb8c` заполняет ~половину точек, финальный вывод на экран (`vs 18f2aadc` / `fs 0f280247`) —
`zero=576`. На Mi 14 с `DM_GFX_SIM_GPU=mali` (те же политики, что на Mali) те же проходы копируют картинку один в один,
то есть дело в драйвере. В `vs 18f2aadc` UV считаются из входа `location=2`, объявленного `float vec4`, через
`OpBitcast` в `uint` (Maxwell читает регистр атрибута как есть и делает `I2F.U32`): формат атрибута целочисленный.
Несовпадение типа входа и формата по спеке Vulkan не определено. Adreno отдаёт биты как есть, Mali (как и Panfrost: тип
регистра в `LD_ATTR` берётся из шейдера) переводит число в объявленный тип, и после bitcast UV — мусор: весь экран
читает один тексель.

`xbg_vertex_retype.h`: если класс входа (`xbg_vertex_input_classes`: float / sint / uint) не совпадает с классом формата
атрибута (`xbg_vertex_format_class`), вход объявляется типом формата, а каждое чтение (весь вектор или компонент через
`OpAccessChain`) идёт через `OpBitcast` обратно в тип шейдера под прежним id. Шейдер получает те же биты, что на Switch.
Вариант модуля строится в `draw()` после выбора форматов атрибутов, на шейдер и код (2 бита на location), и кешируется
в `Shader::retyped`; ключ warm-up — `<shader>#vi<код>`. Непонятное использование входа (не load и не access chain) —
отказ, тогда остаётся базовый модуль; в лог пишется `NVN vertex input retype ... refused`. `DM_GFX_VTX_RETYPE=1/0`,
по умолчанию включено не на Adreno; на Adreno выключено (там всё как было). Проверки:
`tests/vertex_retype_test.cpp` (синтетический модуль; с аргументами переписывает файлы SPIR-V), все 544 вершинных
шейдера D3 переписаны в uint и в sint и прошли `spirv-val --target-env vulkan1.1`.

### Кэш текстур ASTC (`DM_GFX_ASTC_CACHE`, setup шаг 9)

Как оверлей DOOM 2016 (KB TEX-03), только иначе устроен: в D3 текстуры — `Textures/*.tex` в CPK, NVN packaged texture (SNO-заголовок,
блоб `NvFD` с блоками `NvBH`: тип 2 — описание: размер хранилища, ширина, высота, формат NVN, уровни, 16 смещений уровней с +40,
log2 высоты блока в GOB +108; тип 3 — само хранилище block-linear, ровно в том виде, в каком игра кладёт его в память). BC1 у D3 —
3.6 ГБ из 5.7 ГБ BC, а блока ASTC в 8 байт нет, так что подменить блоки «на месте», как DOOM, нельзя. Поэтому:

- `tools/d3_astc_cache.py` (setup шаг 9, отдельно `setup astc`): все BC-текстуры слитого вида RomFS и языковых пакетов

  хозяина (13.11): у каждой текстуры мип 0 ≥ 42 дБ против декодированного BC; шаги по порядку, берётся первый, что дотянул:
  BC1 — 6x6 / 5x5 / 4x4 `-fast`, 4x4 `-medium`, 4x4 `-thorough`; BC2/BC3 — 4x4 `-fast`, `-medium`, `-thorough`; не дотянул ни один —
  текстура не попадает в кэш и остаётся на BC-декоде. Нулевые блоки ASTC → void-extent прозрачного чёрного (TEX-04). Пак

### Портал дерзаний без сети (issue #27) — 16.11.2026

Запрос: 15-я печать Алтаря обрядов стоит тайник портала дерзаний, без серверов его не получить. Данные — 29 настоящих недельных
дампов из d3hack (`examples/config/d3hack-nx/rift_data`), вшиты в libdm: `dm/host/hle_d3_rift_data.inc` (148 КБ, генератор
`tools/d3_rift_inc.py`, проверяет в каждом файле снимки портала / героя / аккаунта).

Как игра получает портал (2.7.7): меню 0x181700 → 0x69ab0 → 0x69990 → StorageGetPublisherFile(user, "challengerift_config.dat") 0x66b10;
колбэк файла 0x726d0 разбирает `ChallengeData` (нужен номер), 0x72880 просит `challengerift_<номер % 10>.dat`, 0x72a70 разбирает

Слой хранилища отвечает со своего сетевого потока через 0x70850, который ставит колбэк в очередь главного потока (0x7b970).

d3hack хукает sOnGetChallengeRiftData и подменяет неудачный ответ файлами с SD (старый, закомментированный вариант — хук
StorageGetPublisherFile). У нас хук — сам StorageGetPublisherFile 0x66b10: два файла испытания отдаём сразу из вшитых дампов через

## Очередь заданий игры на хосте (`DM_D3_JOBS`), issue #18 — 13.11.2026

Отчёт (Poco F8 Ultra, SM8850 / Adreno 840, Android 17, 0.2.9): падение в случайный момент, чаще после портала в город и
у кузнеца. Три падения одного вида: `CRASH sig=11 pc=main+0x13839c | 0x10388c | 0x103888`,
`bt main+0x515bd0 main+0x515b50 main+0x9a54` — рабочий поток `JobWorker` (0x515b60) на первых чтениях только что взятого
задания. Задания 0x1382f0 (ставит 0x133030) и 0x103830 (ставит 0x102cf0) получают 16-байтовый описатель
`{список, первый, сколько}` из кадра стека вызвавшего, то есть главного потока игры (он идёт на хостовом стеке:
`x19=0x7b…`). На месте описателей лежали чужие кадры (`{1.0f, 1, указатель в кучу}`, `{указатель, сохранённый x29}`,
`{3, адрес возврата в main}`): главный поток уже вышел из 0x102cf0 / 0x133030, а рабочий поток только начал их задание.

Пул игры (один, `*(main+0x114aa18)`, два потока): кольцо на 1024 `{fn, arg}` без блокировок (LL/SC по `tail`), слово
состояния, счётчик бодрствующих потоков, `LightEvent` и `Semaphore` из SDK. Ставит, «пинает» и ждёт только главный
поток (0x40810, 0x3ee30). Перебор всех чередований (модель шагов 0x515f70 / 0x516060 / 0x5160d0 / 0x515b60, около 60
программ; семафор SDK поверх наших SVC 0x1a–0x1d так же) нарушений не дал: при одном ставящем потоке задание не может
стартовать после возврата из ожидания. Пул ломают три вещи: возврат `tail` на тот же индекс, пока поток стоит между
чтением слота и store-exclusive (1024 взятия); второй поток в ожидании (оно заканчивается записью «состояние = 0»,
следующее ожидание выходит сразу, задания остаются в кольце); ожидание изнутри задания, которое главный поток сам
выполняет из ожидания. Кадр 0x3ee30 зовёт ожидание (0x10e890) на любом пути, в том числе как «насос» экрана загрузки
0x3d4d0 из блокирующих загрузок потоков вида 0 (главный и `UISpriteThread`) в первые ~2 с после загрузки. По трём
отчётам (только регистры упавшего потока) выбрать причину нельзя; хуки `hle_d3_ui.c` / `hle_d3_icons.c` и трекер
страниц пул не трогают (игрок был с геймпадом, тапов не было).

Исправление не зависит от причины (`dm/host/hle_d3_jobs.c`, `DM_D3_JOBS=1` по умолчанию): вход постановки 0x515f70,
ожидания 0x5160d0 и цикл рабочего потока (0x515ba0) уходят в хостовый пул без блокировки на пути задания: кольцо на 4096
ячеек для многих ставящих и берущих (номер последовательности в ячейке, по одному CAS на постановку и взятие), атомарный
счётчик «поставлено и не закончено» (+1 до постановки, −1 после возврата из задания). Ожидание берёт и выполняет
задания и возвращается при счётчике 0 — с любого потока, при любом слове состояния; изнутри задания оно ждёт всех, кроме
заданий, в которые вложено. При пустом кольце ожидание 30 мкс опрашивает (`DM_D3_JOBS_SPIN_US`), потом спит на futex,
который будит закончившееся задание; рабочий поток при пустом кольце спит на своём futex, его будит постановка
(`DM_D3_JOBS_WORKER_SPIN_US`, по умолчанию 0 — без опроса). Задание не может стартовать после возврата из ожидания,
следующего за его постановкой. Потоки, их стеки, запуск и выход — прежние; все места сверяются пословно, на другой
сборке остаётся пул игры.

Замеры (`DM_D3_JOBS_STATS=1` по умолчанию), раз в минуту строка `[d3jobs] … pool host|game: кадров, заданий на кадр
(доля на рабочих потоках), push->start среднее и p99, время главного потока в ожидании на кадр, contention (повторы CAS
кольца, засыпания, пробуждения, выполнено постановкой при полном кольце)`. `DM_D3_JOBS=0` — пул игры; с замерами его
постановка и ожидание идут через пробу (задание обёрнуто, код пула исполняется как есть), строка та же, чтобы сравнить
на телефоне; `DM_D3_JOBS_STATS=0` — код игры не тронут. Ещё в лог: первые ожидания изнутри задания и (красным) первые
вызовы не с главного потока — если такие строки появятся, причина найдена.

Проверки: `dm/host/tests/t_d3_jobs.c` на Linux x86-64 (два рабочих потока, описатели в кадре стека, ожидания изнутри
заданий, второй ждущий поток, переполнение кольца) — ~10 млн заданий на прогон, ни одного задания на мёртвом описателе,
ни одного зависания; ThreadSanitizer чист. Пропускная способность там же (`t_d3_jobs bench`, пачка: N постановок +
ожидание), первая версия (очередь под мьютексом) → кольцо: пустые задания 8 / 128 / 1200 в пачке — 1,9 → 4,1,
3,3 → 8,4, 5,3 → 13,2 млн заданий/с; задания ~0,1 мкс — 0,75 → 3,1, 2,6 → 7,1, 5,9 → 9,9; задания ~1–2 мкс — 0,28 → 0,70,
1,1 → 2,0, 2,2 → 2,2 (упор в сами задания). Сборка APK. На телефоне не проверено.

1. *Без мультиплеера (регрессия):* обычный запуск, 2–3 мин игры: в boot.log нет строк `[ldn]` / `[coop]` / `[net] lan:`; fps как на 0.2.12.

   вход второго игрока кнопкой на геймпаде. Отключить геймпад: `[coop] … removed: player 2's npad disconnected` (игра покажет свой экран).

## Ядра CPU: размещение потоков по ёмкости, повтор после onResume, ⚙ «Ядра CPU» (issue #23) — 15.11.2026 (ветка `wt/cpu`)

Отчёт (#23, Helio G99 = 2 × A76 + 6 × A55): через ~30 с игры низкий fps и «замедленная съёмка», не тепло; выход в недавние
приложения и обратно или запуск записи экрана делают игру быстрой ещё на 30–40 с; Magisk-модуль Encore (планировщик /
говернор) лечит у двоих. Просят выбор «потоки на мощных ядрах / на всех».

**Что было до этого (0.2.15):** привязывался только поток, который выводит кадр (`nvn-translate`; с `DM_NVN_SYNC=1` — гостевой),
к ядрам с наибольшим `cpuinfo_max_freq` (`vulkan_present.cpp fastest_cores`, на G99 = cpu6-7, оба A76), проверка раз в 120
выводов. Главный поток игры (самый загруженный гостевой), два `JobWorker` пула заданий (`DM_D3_JOBS`) и прочие гостевые потоки
не размещались вовсе и никак не отслеживались. G99 старое правило не путает (A76 2.2 ГГц > A55 2.0 ГГц), так что дело не в
маске транслятора. Вероятная причина #23 (не доказано, логов игроков с новой сборкой ещё нет): после окончания стартового буста
(≈30 с; рецентс и запись экрана дают новый буст) планировщик / говернор MediaTek уводит главный поток и воркеры на A55 и держит
их там; у нас не было ни средства вернуть их, ни строки в логе, где они идут.

**Что сделано:** общий модуль `port-common/modules/cpu-place` (KB APP-14; план — DOOM 2016 `cpu_topo.c`, APP-05).
- План по ёмкости: роли translate (как в DOOM), main (главный гостевой поток), jobs (гостевые с именем `JobWorker*`), прочие гостевые.
  Режимы ⚙ «Ядра CPU» (`DM_CPU_CORES`, сразу + со следующего старта): **Авто** — G99: транслятор один на cpu7, главный на cpu6-7,
  воркеры и прочие везде, кроме cpu7; 4+4: транслятор cpu7, главный и воркеры на трёх остальных больших; флагманы (8 Gen 3
  2+3+2+1): транслятор на X4, главный и воркеры на пяти A720, прочие свободны; все ядра одинаковые — ничего. **Только мощные** —
  все игровые потоки на ядрах вне малого кластера (G99: всё на cpu6-7). **Все ядра** — без привязок (решает система; ранее
  поставленные маски снимаются).
- Поток `dm-cpu`: ставит маски, проверяет каждые 2 с (`DM_CPU_CHECK_MS`) и сразу после возврата в игру (`nativeFocus` 2 / 3: сразу и
  каждые 0.5 с в течение 4 с), в фоне (onStop) не трогает ничего. Маска, изменённая системой, ставится снова и пишется в лог.
- Диагностика: раз в 60 с (первая через 30 с) `[cpu] where`: сколько замеров главный / транслятор / воркеры оказались на малом
  кластере и на каких ядрах; cpuset-группа главного потока при каждой смене (`/top-app` → `/foreground`…).
- `vulkan_present.cpp`: старый пин только при маркерах `gfx-pin-cpu` / `gfx-no-pin` / `gfx-ab-target=pin`; без них поток вывода
  ставит модуль. `DM_CPU_TOPO=index` = старое правило (A/B).

Проверка без телефона: `t_cpu_place.c` (163: 41 проверка DOOM + поддельные sysfs G99 2+6, SD680 4+4, D8300 1+3+4, 8 Gen 3
2+3+2+1, SD450, 6+2, 1+1+6, 8 Elite, SD439 × режимы × источники) и `t_cpu_place_rt.c` (22: настоящие потоки в WSL на поддельной
G99: маски, повтор после «системы», фон, resume, живые режимы, маркеры). На телефоне не проверено.

**Проверка на телефоне (boot.log):**
1. `[cpu] topology: 8 cpus, ranked by capacity: …` (Mi 14 Ultra: `cpu7 1x X4 … | cpu2-4 3x A720 … | cpu5-6 2x A720 … | cpu0-1 2x A520 … (little)`)
   и `[cpu] plan: mode=auto rule=capacity translate=7 (80) main=2-6 (7c) jobs=2-6 (7c) other guests=free (0); before the module: translate=7, …`.
2. (Строки `[pc] cpu-place: …` в D3 нет: `pc-core` в публичный репозиторий не внесён — в его `pc.h` локальный путь.)
3. После первых кадров: `[cpu] placed (…, mode auto): translate tid N (nvn-translate) -> 7; main tid N (main) -> 2-6; jobs tid N (JobWorker0) -> 2-6; jobs tid N (JobWorker1) -> 2-6; K other guest threads -> free`.
4. Через 30 с и далее раз в минуту `[cpu] where …: translate on little 0/…; main on little 0/…; jobs on little 0/…; masks set again N …; main cpuset /top-app`.
5. Рецентс и обратно: `[cpu] background: placement checks paused`, затем `[cpu] resume: N thread(s) had other masks (…)`.
6. ⚙ → «Ядра CPU» → «Только мощные»: `[cpu] plan (gear, live): mode=big … translate=2-7 (fc) …` и `[cpu] placed (mode, mode big)`.
7. `[cpu] … mask found X (set Y): set again` = система переписала маску (HyperOS); `left free but its mask is …` в режиме «Все» = система сузила.

## Подсказки разгона системе: ADPF с фиксированным бюджетом, «нагрузка растёт», GameState (issue #23) — 15.11.2026 (ветка `wt/adpf`)

Вторая половина #23 (первая — размещение потоков, раздел выше): после конца стартового буста MediaTek (PowerHAL / FPSGO) частоты
падают, игра в «замедленной съёмке», пока рецентс или запись экрана не дадут новый буст. Здесь — официальные API Android, которыми
игра сама просит частоты. Общий модуль `port-common/modules/adpf-boost` (KB PERF-E14 + PERF-X08).

**Что было (0.2.15):** ADPF-сессия из nx2android: цель = период пейсера (когда кадры медленные и ярус падает, подсказка просила
*меньше* частоты), участники пересматривались раз в 300 выводов (при 20 fps = 15 с), главный поток и `JobWorker` попадали только
если сами набирали 15 % ядра, не было `setPreferPowerEfficiency`, потерянная сессия (EPIPE) не открывалась снова, сводки не было.

**Что сделано (`dm/android/perf_android.c`, решения — `perf_boost.h`):**
- Из DOOM Eternal (PERF-E14, ETR `26ece9a` / adpf `53e8f89`): цель = min(период, `DM_ADPF_BUDGET_MS=33.33`); пересмотр участников
  каждые `DM_ADPF_SCAN_MS=5000`; `setPreferPowerEfficiency(false)` (Android 15); учёт кодов возврата, EPIPE → переоткрытие через 5 с;
  кадр > 1 с или > 250 мс при < 25 % CPU — пауза, не отчёт; строка `[perf] ADPF 10s:` (отчёты, работа против цели, участники с ядром и
  uclamp.min, min/cur/max частот каждого кластера).
- Участники D3: поток вывода — всегда; главный гостевой поток — с первого скана (уходит после двух сканов < 5 % ядра); `JobWorker*`
  (`DM_CPU_JOB_NAMES`, как в cpu-place) — от 5 % ядра и раньше любых других; прочие потоки игры — от 15 %; не больше 6.
- «Нагрузка растёт»: 3 кадра подряд работа > цели, или целую секунду кадры в среднем на 15 % медленнее цели → подсказка, не чаще
  раза в 500 мс. Android 16 (API 36): `APerformanceHint_notifyWorkloadIncrease(cpu, !gpu)`; Android 14–15: платформенный символ
  `APerformanceHint_sendHint(CPU_LOAD_UP)` из `libandroid.so` (за ним Java `PerformanceHintManager.Session.sendHint`, который `@hide`:
  публичного пути на 13–15 нет; `DM_ADPF_BOOST=2` — только публичный вызов); Android 13 — подсказок нет (в логе). Сброс
  (`notifyWorkloadReset` / `CPU_LOAD_RESET`) при возврате в игру (`nativeFocus` 2/3) и когда закрылся экран загрузки.
- GameState (Java, Android 13): `GameStateHint.java` дважды в секунду, пока игра на экране, спрашивает `nativeGameState` и передаёт
  смену в `GameManager.setGameState`: loading = экран загрузки (`diag.c dm_loadscreen_up`), режим «игра, можно прервать» в игре
  («нельзя прервать», если открывалась локальная игра `dm_ldn_lan_on`), «нет игры» во фронтенде (`touch_android.c
  dm_android_scene_game`). В манифесте уже `appCategory="game"`. Будет ли HyperOS / MediaTek что-то с этим делать — неизвестно.
- Переключатели: `DM_ADPF_BUDGET_MS=33.33`, `DM_ADPF_TARGET_MS=period` (старое поведение), `DM_ADPF_BOOST=0` (без подсказок),
  `DM_ADPF_BOOST_MS=500`, `DM_ADPF_BOOST_FRAMES=3`, `DM_GAME_STATE=0`, `DM_ADPF_POWER_EFF`, `DM_ADPF_SCAN_MS`, `DM_ADPF_MAX_THREADS`,
  `DM_ADPF_DIAG_MS`; `DM_ADPF=0` / `DM_NO_ADPF=1` — без сессии. Пункта в ⚙ нет (параллельная ветка правит те же места ⚙).

Проверка без телефона: `port-common/modules/adpf-boost/test/t_adpf_boost.c` (решения: серии кадров, секунда медленных кадров, лимит
частоты, паузы, выбор участников — главный / воркеры / прочие / уход после двух пустых сканов), обе APK собраны. На телефоне не проверено.

**Проверка на телефоне (boot.log):**
1. `[perf] ADPF switches: DM_ADPF_TARGET_MS=budget(default) DM_ADPF_BUDGET_MS=33.33 … DM_ADPF_BOOST=1 …`.

## Полосы Mali в широком режиме и DRS игры: ⚙ «Динамическое разрешение игры», выравнивание 64, копия для ToneMap, частота GPU (issue #23) — 15.11.2026 (ветка `wt/mali23`)

Отчёт #23 (Helio G99, Mali-G57 MC2, r32p1, 0.2.15): «по форме экрана» + «720p» (1632×720) тонкие цветные полосы через ~92 px под UI
(разбор — KB MALI-16). Причина сужена до 3D-кадра DRS игры: пост-цепочка рендерит 3D в подобласть и растягивает её `PostFX Upscale`.

**DRS игры (main 2.7.7, найдено по строке «Variable Res Percent %6.2f. Device Frame us: %d» в 0x3ee30):** состояние 0x44 байта на
вид (конструктор 0x3cb90, у вида +0x2c0): пороги GPU-времени 14250 / 15250 мкс, шаг 0.05, масштаб 0.7..1.0, пауза 8 кадров после
смены, кольцо 8 последних времён GPU. Регулятор 0x3cd10 раз в кадр (поток рендера 0x428f0) берёт время GPU прошлого кадра (0xeaf60,
таймер NX64NVNCore по ReportCounter), опция игры 0x79 → 1.0. Проход сцены (0x43220, место 0x43c14) берёт размер 3D-цели из 0xebac0
(в handheld — цель док-размера × 0.8) и рисует в (u32)(масштаб × w) × (u32)(масштаб × h) **без округления**. На медленном GPU масштаб
садится на 0.7: широкий handheld 2048×900 → цель 1638×720 → 3D 1146×504 (не кратно 64); 16:9 handheld 1280×0.7 = 896 = 14×64.
Замечание: в широком handheld и при 1.0 3D = 1638 (2048 × 0.8), а окно 1632 — апскейл и тут слегка сжимает (не трогали).

**Что сделано:**

  `off` (всегда 1.0), ⚙ «Динамическое разрешение игры» (вкл. по умолчанию), живо (`nativeSetD3Drs`). `DM_D3_DRS_ALIGN=<n>`: ширина
  3D кратна n — в состояние пишется (⌊масштаб × w / n⌋ × n + 0.5) / w, свой невыровненный масштаб регулятор хранит отдельно;
  по умолчанию 64 не на Adreno (семейство политики, `DM_GFX_SIM_GPU=mali` считается Mali), 0 на Adreno; решается, когда известен GPU
  (`xbg_gpu_policy_family`). Лог `[d3drs] installed …`, `[d3drs] 3D target WxH (window …); width alignment N (…)`, раз в 10 с
  `[d3drs] 10s: DRS auto|off, scale now … (min avg max, changes) -> 3D WxH of …, GPU X ms avg (game target 14.25..15.25 ms …)`.
- `xbg_game.cpp`: перенос ETR `DM_GFX_FEEDBACK_COPY` (5d73072 + c877c73, KB SYNC-06): draw, сэмплирующий свою же цель, читает копию,
  снятую перед draw. По умолчанию вкл. не на Adreno, выкл. на Adreno; лог `NVN same-draw feedback copy DM_GFX_FEEDBACK_COPY=…` и
  `NVN feedback copy shader=<ключ> …` раз на шейдер / биндинг (ждём `703334b9…` = ToneMap).
- `perf_android.c`: в `[perf] ADPF 10s` — `GPU MHz cur C max M`; источник ищется один раз (`[perf] GPU frequency: <путь> …` или
  `no readable GPU frequency; tried …` с ошибкой каждого пути): kgsl gpuclk / devfreq, MediaTek GED `current_freqency`, `gpu_cur_freq`,
  `/proc/gpufreqv2/gpufreq_status`, `/proc/gpufreq/gpufreq_var_dump`, `mali0/device/cur_freq`, `/sys/class/devfreq/*{mali,gpu,g3d,kgsl}*`.

**Проверка:** обе APK собраны, на телефоне не проверено (тестовая сборка «0.2.16 - test issue #23», заметки `work/rel/notes2/test23.md`).
На Mi 14 (Adreno): `width alignment 0 (default: Adreno, off)`, `DM_GFX_FEEDBACK_COPY=0`; строка `[d3drs] 10s` (обычно scale 1.000);

## Общие модули port-common: выход потока на хостовом стеке (HLE-06) и present на своём потоке (PERF-D07) — 16.11.2026 (ветка `wt/pcmods`)

**`thread-exit-hoststack` (KB HLE-06, из DOOM 2016, issues #12/#20 там).** SVC ExitThread звал `pthread_exit` прямо на маленьком
гостевом стеке (Horizon исполняет SVC на стеке ядра, игры дают потокам по 16–64 КиБ); на Samsung S23+ / Android 17 teardown bionic

тот же. Теперь `thread_main` запоминает sp своего pthread-стека перед `dm_thread_enter`, `thread_exit` переходит туда через
`dm_call_on_stack` (новая процедура в `entry.S`) и делает весь teardown там. **Выключателя нет** (чистый фикс, как в D16; модуль и README
port-common выключателя не предусматривают). Строка `[pc] thread-exit-hoststack: applied (guest threads exit on their host pthread
stack, first 0x…; HLE-06)` при первом таком выходе. Вместе с ним пришёл `pc-core` (`dm/host/pc.h`, `hle_pc.c`, `pc_code.h`: функция

## Общие модули port-common, пакет 12: device-fault (APP-16), pvr-cb-barrier (PVR-11), TEX-02, bc-astc-gpu (TEX-18) — 19.11.2026 (`main`)

Все четыре — для GPU без BC и для диагностики; на Adreno путь рисования не меняется (там BC нативный, `DM_GFX_NATIVE_BC=1`, `bc_store`
отдаёт `BC_NATIVE`, до `bcgpu` / `bcastc` дело не доходит). На телефоне ещё не запускались.

- **`device-fault` (FN-64, `ad2a095`, sync_common, 4 правки).** `VK_EXT_device_fault` включается на любом устройстве, где драйвер его даёт
  с фичей `deviceFault` (`DM_GFX_DEVICE_FAULT=0` — выкл.). При потере устройства / сбое fence / зависании GPU `xbg_fatalf` один раз пишет отчёт
  драйвера: тип ошибки, адрес GPU с точностью, коды вендора. Строки: `NVN device fault: enabled (...)` или причина (на стоковом драйвере
  Qualcomm обычно `driver has no VK_EXT_device_fault`), `[pc] device-fault: applied|skipped (...; FN-64)`.
- **`pvr-cb-barrier` (FN-63, `a356a30`, sync_common).** Полный барьер (ALL_COMMANDS → ALL_COMMANDS) сразу после `vkBeginCommandBuffer`
  первичных буферов движка (буфер слота и его пролог) через `xbg_cb_begin`. `DM_GFX_PVR_CB_BARRIER`: 0 / не задан — выкл. (по умолчанию,
  буферы как раньше), 1 — только PowerVR (0x1010), 2 — любой GPU. Строка `[pc] pvr-cb-barrier: applied|skipped (...; FN-63)` при первом
  буфере. Кандидат, не подтверждённый фикс; безопасного режима в D3 нет — включать вручную. Самотест GPU (`xbg_selftest.cpp`) и старый
  2D-рендерер (`xbg_vulkan.cpp`) барьер не получают.
- **TEX-02 (`cbf591a`, вручную как TL2 `c01a30e` = DOS2 `4016472`).** Декодер BC на GPU у D3 был версией 05.11 (байт в байт как у TL2 до
  того коммита). `xbg_bc_gpu.glsl`, `xbg_bc_gpu.h`, `xbg_bc_decode.comp`, `xbg_bc_decode_spv.h` и тесты теперь байт в байт как у DOOM 2016.
  `bcgpu`: самотест `DM_GFX_BC_SELFTEST` (1 по умолчанию: каждый новый конвейер декодирует 2048 известных блоков на устройстве и
  сверяет с CPU; расхождение — этот формат на CPU; 2 — только лог; 0 — выкл.), отправка самотеста через `ptq::submit` (замок очереди
  present-потока, как в TL2 HEAD), `DM_GFX_BC_BARRIER=full` (по умолчанию; `narrow` — старые пары барьеров). Строки:
  `NVN BC decode: self-test fmt=… bad=… -> gpu|cpu`, `NVN BC decode: barriers=full (DM_GFX_BC_BARRIER)`.
- **`bc-astc-gpu` (FN-60 + FN-61, `9a92c70`, вручную по `migration/bc-astc-gpu.md`).** BC1 / BC2 / BC3 / BC7 на пути GPU-декода
  создаются как `VK_FORMAT_ASTC_4x4_UNORM / _SRGB`; после декода каждой партии — ещё один compute-проход (кодер после GameNative), в
  картинку копируются блоки ASTC: 1 байт на тексель вместо 4 у RGBA8. Решение по семейству за самотестом на 285 блоках
  (`xbg_astc_ref_decode.h` взят из DOOM 2016) и самотестами TEX-02. `DM_GFX_BC_ASTC` auto (по умолчанию; на Qualcomm выкл.) / 1 / 0
  (старый путь RGBA8 байт в байт), `DM_GFX_BC_ASTC_CANDS` 3 / 1, `DM_GFX_BC_ASTC_VT` 0 / 1. Отличия от D16 в `xbg_game.cpp`: нет
  `BcVerify` / `bcv::attach` / `subst_cpu` (поэтому `pc_check` пишет «present, DIVERGED 3/18» — так и должно быть), в `BcUpload`
  добавлено поле `partial` (его пишет `copy_from_buffer`), шимы `vkCmd*` / `ptq::submit` / `gpguard::Lock`, `fb_snapshot` копирует `bc_astc`.
  `DM_GFX_BC_DECODE=cpu` выключает и его (кодер нужен GPU-декод). `DM_GFX_BC_BATCH_MB` задаёт и буфер ASTC (четверть выхода декода),
  `DM_GFX_BC_PARTIAL` — частичные загрузки тоже идут через кодер, `DM_GFX_BC6_E5` не задет (BC4 / BC5 / BC6H остаются как были).
- **Как это сочетается с кэшем ASTC (`DM_GFX_ASTC_CACHE`, `astc/d3-astc.pack`).** Порядок для BC-текстуры: `astccache::lookup` нашёл —

  декодированную картинку (а ASTC с GPU тоже `decoded=true`) из пака. Приоритет: пак astcenc (собран setup'ом, лучше) > ASTC с GPU > RGBA8.
  Копии между картинкой из пака и любой другой по-прежнему пропускаются (`NVN astc cache: copy skipped`); копии ASTC-с-GPU ↔ RGBA8 одного

## Кап кадров ведёт экран и подсказки CPU: модуль pace-vote (KB PNH-C03, PNH-C05) — 26.11.2026 (ветка `pc/pace-vote`)

Общий модуль `port-common/modules/pace-vote`; правила взяты по смыслу из peanuts-native `85eeb7a` (igawa6, GPL-3.0-or-later).

**Что было:** цель ADPF = min(период вывода, 33,3 мс): если игра просела до 30, система держала частоты ровно под 30 и вернуться на 60
было нечем. Окно всегда голосовало за 120 Гц; у peanuts 30 кадров на 120-Гц экране шли парами 25 / 42 мс, ровно стало только с
режимом экрана 60 Гц.

**Что сделано:**
- `hle_nvn.c` `dm_pace_cap_hz()`: кап, который выбрал игрок или игра (⚙ 30 / 60, «эко» 30 из своей страницы, `DM_PRESENT_MAX_HZ`,
  закреплённый `DM_PRESENT_HZ`), а не текущий ярус пейсера. Кап из ⚙ теперь меняется сразу (`PaceVote.setCap` → `nvn_present_cap_set`),
  только если игрок выбрал другое значение (тогда `DM_PRESENT_MAX_HZ` из `dm/env` до этого не трогается).
- `perf_android.c`: цель ADPF = период этого капа (60 → 16,67 мс, 30 → 33,33), не меньше одного обновления экрана (`DM_ADPF_TARGET=game`,
  по умолчанию; `=old` — старое правило). Голос окна = самая низкая частота экрана, кратная капу и не ниже max(кап, 60), не выше
  маркера 120 (`DM_VOTE_HZ=cap`, по умолчанию; `=max` — старый голос 120): кап 30 → 60 Гц, кап 60 → 60 Гц, где есть режим 60, выше 60 /
  без капа → 120. Вниз голос идёт только после 5 с на новом значении (`DM_VOTE_HOLD_MS=5000`), вверх — сразу; раз в 5 с голос
  повторяется (новая поверхность в `vulkan_present.cpp` голосует 120). Голос теперь делается и при `DM_ADPF=0`.
- `PaceVote.java`: дважды в секунду, пока игра на экране, отдаёт нативной части частоты режимов экрана текущего разрешения и просит
  у окна режим той частоты, которую выбрал голос (`preferredDisplayModeId`), если она ниже самой быстрой; иначе и на паузе — возвращает
  прежний запрос окна. Общие настройки экрана не трогаются.
- Заметное по умолчанию: при капе 60 панель теперь 60 Гц, а не 120 (кадры те же, меньше расход; касания могут опрашиваться реже).

**Проверка без телефона:** `port-common/modules/pace-vote/test/t_pace_vote.c` (768 проверок), `libdm.so` и APK собраны. На телефоне
не проверено.
